## SIM-004 – SQL Injection (T1190) – Detection Queries

This document outlines the queries and detection logic relevant to SIM-004.
Due to lab design, network-based detection via Security Onion is the authoritative source.
SIEM-based correlation queries are discussed conceptually, not executed.

---

## 1. Detection Scope and Constraints

**In Scope**
- Network-based IDS detection (Suricata)
- HTTP payload inspection
- Attacker → victim attribution
- Temporal correlation with SQL injection execution

**Out of Scope**
- Endpoint detection (no Windows host involved)
- Database audit logs
- Application source logs
- SIEM-based correlation (Splunk not integrated)

---

## 2. Primary Detection Source – Suricata (AUTHORITATIVE)

Suricata alerts generated by Security Onion serve as the primary detection mechanism for this simulation.

Detection is based on:
- Malformed HTTP requests
- SQL logical operators and comment markers
- Policy-based web signatures

---

## 3. IDS Alert Identification (Security Onion)
**Alert Characteristics**
- Signature Category: ET WEB_SERVER
- Detection Type: Web policy violation
- Severity: Medium
- Context: HTTP request containing SQL injection logic

Although not explicitly labeled “SQL Injection,” the alert reliably identifies exploit-related web traffic.

---

## 4. Analyst Pivot Logic (Conceptual Workflow)

A SOC analyst investigating this alert would pivot using the following logic:
1. Identify alert timing
2. Confirm source and destination IPs
3. Review HTTP payload context
4. Correlate with observed application behavior
5. Assess likelihood of successful exploitation

This mirrors real-world SOC triage methodology.

---

## 5. SIEM Queries – NOT APPLICABLE (Documented Limitation)
**Why No Splunk Queries Exist**
- No Splunk Universal Forwarder installed on Security Onion
- No Suricata logs forwarded to Splunk
- No HTTP logs indexed in Splunk for this simulation

As a result, no executable SPL queries were available or validated.  

> This limitation is intentional and documented, not a failure.

---

## 6. Example SIEM Query (Conceptual – NOT EXECUTED)
> ⚠️ The following query is illustrative only and was not executed in this simulation.
```spl
index=suricata
| search signature="ET WEB_SERVER"
| table _time source.ip destination.ip signature http_method uri
| sort -_time
```

This represents how SQL injection–related web alerts would be investigated in a fully integrated SIEM environment.

---

## 7. Detection Logic Summary
| Layer	     | Logic  |
|------------|--------|
| Network	   | Inspect HTTP requests for SQL logic |
| IDS	       | Trigger web policy alert |
| Analyst    | Correlate alert with application behavior |
| SIEM       | Not applicable |

Detection confidence is derived from behavior + context, not alert naming.

---

## 8. Key Takeaways for Detection Engineering
- SQL injection is often detected as generic web traffic anomalies
- Signature names may not explicitly state “SQL Injection”
- IDS visibility depends on network placement
- SIEM correlation is valuable but not required to validate detection

# SIM-003 – SQL Injection (T1190) – Detection Queries

This file documents the detection logic and investigative queries relevant to
SIM-004, which demonstrates **SQL injection exploitation** against a vulnerable
web application (DVWA).

This simulation reflects a **network-centric detection model**, where:
- **Suricata IDS alerts** are the authoritative detection signal
- **SIEM-based SPL correlation is intentionally unavailable** due to lab design

Detection logic is therefore documented from a **SOC analyst and detection
engineering perspective**, even when queries are conceptual rather than executed.

---

## 1. Baseline Web Activity (Normal HTTP Requests)

**Purpose:**  
Establish expected, non-malicious HTTP request behavior for comparison during
investigation.

> ⚠️ Baseline traffic was observed directly via inline network visibility.
> No SIEM-indexed HTTP logs were available for querying.

Baseline Characteristics:
- Simple numeric input
- No SQL operators
- Normal application response

```text
Example Input:
1
```

What This Confirms:
- Application responds normally to valid input
- No backend query manipulation
- Establishes a clean baseline for contrast

---

## 2. PRIMARY Detection – IDS Alert (Suricata)

Purpose:  
Detect suspicious or malicious HTTP traffic indicative of SQL injection attempts.

Authoritative Detection Source:  
Suricata alerts generated by Security Onion.

Detection is based on:
- SQL logical operators (OR, UNION)
- Comment markers (--, #)
- Malformed or abnormal HTTP request patterns

This represents the primary detection signal for SIM-004.

---

## 3. IDS Alert Identification (Observed Signal)

Observed Alert Characteristics:
- Signature Category: ET WEB_SERVER
- Detection Type: Web policy violation
- Severity: Medium
- Context: HTTP request containing SQL injection logic

Why This Matters:
- IDS signatures often detect behavior, not exploit names
- Generic web alerts can still indicate high-risk exploitation
- Timing and payload content provide detection confidence

---

## 4. Behavioral Validation (Application-Layer Correlation)

Purpose:  
Correlate IDS alerts with observable application behavior to confirm exploitation.

Observed Injection Payloads:
```text
1' OR '1'='1
1' OR 1=1-- -
1' UNION SELECT user, password FROM users-- -
```

Observed Application Behavior:
- Multiple database records returned
- User credential data disclosed
- Backend query logic manipulated

What This Proves:
- IDS alert corresponds to real exploitation
- Detection validated through application impact
- Confirms attacker success, not just probing

---

## 5. Analyst Investigation Workflow (SOC Perspective)

Purpose:  
Document how a SOC analyst would investigate this alert in practice.

Analyst Pivot Logic:
1. Identify IDS alert timing
2. Confirm source and destination IP addresses
3. Inspect HTTP payload content
4. Correlate with observed application responses
5. Assess exploitation success and severity

This mirrors real-world SOC triage methodology when SIEM correlation is limited
or unavailable.

---

## 6. Supplemental SIEM Query (Conceptual – NOT EXECUTED)

Purpose:  
Illustrate how this detection would be queried in a fully integrated SIEM.

> ⚠️ This query is illustrative only and was not executed in this simulation.
```spl
index=suricata
| search signature="ET WEB_SERVER"
| table _time source.ip destination.ip signature http_method uri
| sort -_time
```

Why This Is Included:
- Demonstrates detection engineering intent
- Shows how network alerts would be operationalized
- Documents future SIEM integration path

## 7. Cross-Layer Detection Summary
| Layer	          | Detection Logic   |
|-----------------|-------------------|
| Application     |	Abnormal response behavior confirms injection  |
| Network	        | Malicious HTTP payloads observed inline  |
| IDS	            | Suricata alert triggered   |
| SIEM            |	Not applicable (by design)  |

Detection confidence is derived from behavior + context, not signature naming alone.

---

## 8. Key Detection Engineering Takeaways
- SQL injection is often detected as generic web anomalies
- Signature names may not explicitly say “SQL Injection”
- Network placement is critical for visibility
- SIEM correlation improves scale, not validity
- Detection can be confirmed without endpoint telemetry

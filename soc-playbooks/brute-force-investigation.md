# Brute Force Investigation Playbook

## Executive Summary

This playbook provides a structured methodology for investigating brute force authentication attacks within an enterprise Security Operations Center (SOC). The objective is to determine whether repeated authentication failures represent normal user behavior, password guessing, automated brute force activity, or an active account compromise.

The investigation follows a repeatable workflow that validates the alert, gathers context, correlates authentication, endpoint, and network telemetry, determines malicious intent, and recommends appropriate containment and response actions.

Although examples reference Microsoft Sentinel, Splunk Enterprise, Windows Security Events, Sysmon, and Security Onion, the investigative methodology is applicable across modern SIEM and XDR platforms.

## Scenario Overview

A security monitoring platform generated an alert after detecting multiple failed authentication attempts against a Windows account within a short period of time.

The objective of the investigation is to determine whether the activity represents:

- Normal user error
- Password guessing
- Automated brute force activity
- Password spraying
- Successful account compromise

---

## Objectives

- Validate the alert
- Identify the targeted account
- Determine the source of authentication attempts
- Correlate authentication activity across multiple data sources
- Determine whether the attack succeeded
- Contain compromised accounts if necessary

---

# Validate the Alert

The first step is to validate that the alert accurately represents suspicious authentication activity and is not a false positive.

Confirm:

- Alert severity
- Alert time
- Detection rule
- Source host
- Target account
- Source IP address
- Number of failed attempts

Determine whether the alert was generated by:

- Microsoft Sentinel Analytics Rule
- Microsoft Defender
- Splunk Detection
- Security Onion
- Another security platform

---

# Gather Context

Collect additional context before determining whether the activity is malicious.

Gather:

## User Context

- Username
- Department
- Privileged account
- Administrative permissions
- Recently changed password
- Normal working hours
- Typical login locations

## Host Context

- Workstation or server
- Domain joined
- Critical asset
- Normal login destination

## Network Context

- Source IP address
- Internal or external source
- VPN usage
- Geographic location
- Known malicious IP reputation

---

# Investigate

Investigate authentication activity across multiple telemetry sources.

## Windows Security Events

Review:

- Event ID 4625 (Failed Logon)
- Event ID 4624 (Successful Logon)
- Event ID 4740 (Account Lockout)
- Event ID 4648 (Explicit Credential Logon)
- Event ID 4672 (Special Privileges Assigned)

Questions to answer:

- How many failures occurred?
- Were attempts rapid or spread over time?
- Did authentication eventually succeed?
- Was an account locked?
- Was a privileged account targeted?

---

## Endpoint Investigation

Review endpoint telemetry for activity occurring after a successful login.

Look for:

- PowerShell execution
- Command Prompt activity
- New processes
- Remote administration tools
- Suspicious scheduled tasks
- Registry modifications

Useful Sysmon Events:

- Event ID 1 – Process Creation
- Event ID 3 – Network Connection
- Event ID 11 – File Creation
- Event ID 13 – Registry Modification

---

## Identity Investigation

Determine whether the account behavior is normal.

Review:

- Previous login history
- MFA events
- Password reset events
- Privilege changes
- Group membership modifications
- New administrator assignments

Questions:

- Does the user normally log into this machine?
- Is this login occurring during normal business hours?
- Is the source location expected?

---

## Network Investigation

Review network telemetry for suspicious connections.

Investigate:

- Outbound connections
- Lateral movement
- Remote Desktop activity
- SMB traffic
- LDAP authentication
- Kerberos authentication
- DNS requests

Security Onion data sources:

- Zeek
- Suricata
- PCAP (if available)

---

# Correlate the Evidence

Correlate information across all available telemetry sources.

Examples:

- Failed logons followed by a successful login
- Successful login followed by PowerShell execution
- Successful login followed by suspicious outbound network traffic
- Multiple hosts targeting the same account
- Multiple accounts targeted from a single IP

The objective is to determine whether individual events form part of a larger attack sequence.

---

# Determine Impact

Determine whether the activity represents:

- User typing an incorrect password
- Automated password guessing
- Password spraying attack
- Successful compromise
- Privilege escalation
- Lateral movement

Assess:

- Number of affected users
- Number of affected systems
- Privilege level
- Business impact

---

# Respond

If malicious activity is confirmed:

- Disable or lock the compromised account
- Reset the user's password
- Revoke active sessions
- Isolate affected endpoints if necessary
- Block malicious IP addresses
- Escalate according to incident response procedures
- Document findings
- Continue monitoring for additional activity

---

# Microsoft Sentinel Investigation

Example KQL:

```kql
SecurityEvent
| where EventID == 4625
| summarize FailedAttempts=count() by Account, IPAddress
| order by FailedAttempts desc
```

Successful logons after failures:

```kql
SecurityEvent
| where EventID in (4624,4625)
| project TimeGenerated, Account, EventID, Computer, IPAddress
| order by TimeGenerated desc
```

---

# Splunk Investigation

Failed logons:

```spl
index=winevent_security EventCode=4625
| stats count by Account_Name, Workstation_Name, Source_Network_Address
| sort -count
```

Successful logons:

```spl
index=winevent_security EventCode=4624
```

Account lockouts:

```spl
index=winevent_security EventCode=4740
```

---

# Security Onion Investigation

Review:

- Zeek conn.log
- Zeek kerberos.log
- Zeek smb.log
- Zeek dns.log
- Suricata alerts
- Full packet capture (if available)

Look for:

- Multiple authentication attempts
- SMB enumeration
- LDAP queries
- Kerberos failures
- Lateral movement indicators

---

# Evidence Checklist

- Alert details
- Source IP
- Username
- Destination host
- Authentication timeline
- Windows Event Logs
- Sysmon events
- Network telemetry
- Security Onion evidence
- Microsoft Sentinel investigation
- Splunk investigation
- Screenshots
- Timeline of events

---

# Lessons Learned

- Authentication events should always be correlated with endpoint and network telemetry.
- Successful logons following repeated failures require immediate investigation.
- Multiple failed logons alone do not confirm malicious activity.
- Context is essential before determining malicious intent.
- Evidence correlation reduces false positives and improves investigation accuracy.

---

# Interview Response

> "When investigating a brute force alert, I first validate the alert and gather context around the user, host, and source IP. I review Windows Security Events such as Event IDs 4625, 4624, and 4740 to understand the authentication sequence. I then correlate endpoint telemetry for any suspicious processes launched after a successful login, along with network telemetry for outbound connections or lateral movement. Finally, I determine whether the activity represents normal user behavior or an account compromise and initiate appropriate containment actions such as password resets, account disabling, or host isolation if necessary."

---

# Analyst Notes

A brute force investigation should never rely solely on authentication logs. Analysts should correlate authentication, endpoint, identity, and network telemetry to build a complete understanding of attacker behavior before making containment decisions.
